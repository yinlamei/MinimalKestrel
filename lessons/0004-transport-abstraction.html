第 04 课 · Transport 抽象层 —— Socket 可以被替换吗？

预计阅读 12 分钟 依赖倒置 四层架构的物理边界

现在我们的代码有什么耦合？

打开你的 HttpConnection.cs，第一行 using System.Net.Sockets;，然后整个类里到处是 _socket.ReceiveAsync()、_socket.SendAsync()、_socket.Shutdown()、_socket.RemoteEndPoint。

HttpConnection 就是 Socket 的薄壳 —— 换传输 = 重写整个 Connection。这违反了 Kestrel 四层架构的核心原则：

① KestrelServer         — 监听循环
② Transport 层           — "我给你一条双向字节通道"  ← 这层应该可替换
③ Protocol Layer         — HttpConnection ← 不应该知道底下是 Socket
④ Application Pipeline  — 中间件管道
依赖倒置原则在这里的具体应用：Connection 应该依赖一个"字节通道"的抽象，而不是 Socket 本身。Socket 是 Transport 层的实现细节，Connection 层不应该感知它。这样换 QUIC、换 Pipe、换 WebTransport，Connection 层一行不动。

Transport 接口应该长什么样？

在动手写接口之前，先想清楚：Connection 到底需要 Transport 提供什么？

回看我们的 HttpConnection，它对 Socket 只做了这几件事：

  1. 读字节 — await _socket.ReceiveAsync(buffer, ct)
  2. 写字节 — await _socket.SendAsync(bytes, ct)
  3. 查对端地址 — _socket.RemoteEndPoint?.ToString()
  4. 关连接 — _socket.Shutdown() + _socket.Close()
  5. 禁 Nagle — _socket.NoDelay = true（Socket 特有优化）

抽成接口：

// 我们的简化版 Transport 接口
// Kestrel 里对应的是 abstract class TransportConnection

public interface ITransportConnection : IAsyncDisposable
{
    // 核心：双向字节流
    Task<int> ReadAsync(Memory<byte> buffer, CancellationToken ct = default);
    Task WriteAsync(ReadOnlyMemory<byte> buffer, CancellationToken ct = default);

    // 连接信息
    string? RemoteAddress { get; }
    string? LocalAddress { get; }

    // 控制
    CancellationToken Closed { get; }
}

注意几个设计决策：

  • ✅ 用 Memory<byte> 代替 byte[] + offset + count — .NET 现代写法，Span/Memory 支持连续的任意类型内存，性能更好
  • ✅ ReadAsync 返回 Task<int> — 和 Socket.ReceiveAsync 语义对齐，0 = 对端关闭
  • ✅ Closed 令牌 — 连接层可以等待传输层主动关闭，不需要轮询
  • ❌ 没有 NoDelay — 这是 Socket 专属优化，不属于"字节通道"的契约。SocketTransport 实现里自己设

SocketTransport —— 第一个实现

把 Socket 包装成接口实现就叫 SocketTransport：

// Transport 层的默认实现：基于 Socket
public class SocketTransport : ITransportConnection
{
    private readonly Socket _socket;
    private readonly CancellationTokenSource _closedCts;

    public string? RemoteAddress { get; }
    public string? LocalAddress { get; }
    public CancellationToken Closed => _closedCts.Token;

    public SocketTransport(Socket socket)
    {
        _socket = socket;
        _socket.NoDelay = true; // Socket 专属优化，放在 Transport 实现里

        RemoteAddress = socket.RemoteEndPoint?.ToString();
        LocalAddress = socket.LocalEndPoint?.ToString();

        _closedCts = new CancellationTokenSource();
    }

    public async Task<int> ReadAsync(Memory<byte> buffer, CancellationToken ct = default)
    {
        try
        {
            var n = await _socket.ReceiveAsync(buffer, ct);
            if (n == 0) _closedCts.Cancel(); // 对端关闭
            return n;
        }
        catch when (!ct.IsCancellationRequested)
        {
            _closedCts.Cancel();
            throw;
        }
    }

    public async Task WriteAsync(ReadOnlyMemory<byte> buffer, CancellationToken ct = default)
    {
        await _socket.SendAsync(buffer, ct);
    }

    public async ValueTask DisposeAsync()
    {
        try { _socket.Shutdown(SocketShutdown.Both); } catch { }
        try { _socket.Close(); } catch { }
        _closedCts.Dispose();
        await Task.CompletedTask;
    }
}

重要：Kestrel 用 Pipe，不是 Stream

我们这个接口看起来就是个 Stream 对吧？Kestrel 当年也用 Stream，但 2.1 之后换成了 System.IO.Pipelines。区别在于：

维度StreamPipe
内存管理每次 Read 调用者提供 buffer（可能 new byte[]）Pipe 自己管理内存池（MemoryPool<T>），避免分配
消费模型Read → 拷贝到你 buffer → 消费Reader 直接拿到 PipeWriter 写入的内存引用，零拷贝
背压靠 Socket 自己Pipe 内置 CanWrite / FlushAsync 背压机制
适用场景简单异步 I/O高性能、高并发、需要零拷贝
Kestrel 的 TransportConnection 抽象类暴露两个 Pipe：Input（PipeReader）和 Output（PipeWriter）。Http1Connection 读请求就是从 Input.ReadAsync() 拿内存，直接解析；写响应就是往 Output.WriteAsync() 写内存。全程零分配，这是 Kestrel 能跑到每秒几十万请求的关键之一。
我们这节课先不用 Pipe。先把接口抽象层建好，理解依赖倒置的结构。下一阶段可以引入 Pipe 替换 Stream，体验真正的零拷贝。Pipe 是 .NET 高吞吐 I/O 的重头戏，值得单独一课。

ConnectionFactory 也跟着拆

现在 Program.cs 里的 Accept 循环：

// v0.3 版本 — Program.cs 知道 Socket
while (true) {
    var socket = await listener.AcceptAsync();     // ← 直接拿到 Socket
    var conn = new HttpConnection(socket);          // ← 直接传给 Connection
    _ = RunConnectionAsync(conn);
}

拆 Transport 之后，Accept 循环变成：

// v0.4 版本 — Transport 层包装 Socket，ConnectionFactory 负责创建 Connection
while (true) {
    var socket = await listener.AcceptAsync();
    var transport = new SocketTransport(socket);   // ← Transport 层包装
    var conn = new HttpConnection(transport);       // ← Connection 只依赖接口
    _ = RunConnectionAsync(conn);
}

此时 Program.cs 扮演了 Kestrel 的 KestrelServerImpl + ConnectionFactory 组合角色。未来多 Transport 场景下，会有一个 TransportManager 管理多个监听（HTTP + HTTPS + QUIC），每个 Accept 出的连接先过对应的 Transport 包装，再统一丢给 ConnectionFactory。

  2. 新建 SocketTransport.cs — 接口的 Socket 实现
  3. 重构 HttpConnection.cs：构造函数从接收 Socket 改为接收 ITransportConnection，内部所有 _socket. 改为 _transport.
  4. 改 Program.cs：Accept 后先 new SocketTransport 再传给 HttpConnection

重构的自检清单

  • ✅ HttpConnection.cs 里不再出现 using System.Net.Sockets
  • ✅ HttpConnection.cs 里不再出现 Socket 类型
  • ✅ HttpConnection 构造函数参数是 ITransportConnection
  • ✅ Program.cs 是唯一知道 Socket 类型的文件（除了 SocketTransport 自己）

Kestrel 源码里的对应

  • 👉 TransportConnection.cs（抽象类）— Kestrel 版本的 ITransportConnection，比我们的复杂很多：有 Input Pipe、Output Pipe、ConnectionClosed 令牌、RemoteAddress、LocalAddress、TransportFeatures 字典
  • 👉 SocketsTransportConnection.cs — Socket 实现。它在后台跑两个循环：一个从 Socket 读 → 写入 Input Pipe，一个从 Output Pipe 读 → 写到 Socket
  • 👉 QuicTransportConnection.cs — QUIC 实现。QUIC 有多个 Stream，所以这个 Transport 会为每个 Stream 创建子 ConnectionContext
  • 👉 观察两个 Transport 实现的共同模式：Transport 层负责字节搬运，Protocol 层负责字节解析，两层之间用 Pipe 解耦

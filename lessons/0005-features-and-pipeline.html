第 05 课 · Features 字典 —— Pipeline 怎么拿到请求/响应？

预计阅读 15 分钟 四层架构最后一块拼图 业务逻辑从 Connection 里剥离

现在我们的 Connection 有什么越界？

打开 HttpConnection.cs 看 HandleRequest 方法 — 它做了什么？

  1. 检查 Method 是不是 GET（HTTP 协议层面的事，Protocol Layer 该做的）
  2. 根据 Path 返回不同内容（这就是业务逻辑，应该在 Application Pipeline）
  3. 设置 StatusCode / SetText（HTTP 响应格式，Protocol Layer 的事）
越界了！一个 Connection 不应该知道"访问 /hello 返回什么"、"访问 /time 返回什么"。它应该只做三件事：读字节 → 解析成 HTTP 语义 → 把语义塞进一个统一的数据包 → 交给上层。至于上层怎么路由、怎么生成响应，跟 Connection 无关。

Kestrel 用什么当这个"统一的数据包"？—— Feature 接口集合。

Feature 接口集合是什么？

Kestrel 不为 Pipeline 定义一个巨大的 IHttpContext 接口，而是拆成了一组单一职责的小接口：

Feature 接口职责谁填的
IHttpRequestFeatureMethod, Path, Headers, BodyProtocol Layer（Http1Connection 等）
IHttpResponseFeatureStatusCode, Headers, Body, HasStartedProtocol Layer 初始化，Pipeline 填写
IHttpConnectionFeatureRemoteAddress, LocalAddressProtocol Layer（从 Transport 拿）
ITlsConnectionFeatureClientCertificateProtocol Layer（TLS 握手后）
IHttpRequestIdentifierFeatureTraceIdentifier（请求唯一 ID）谁都行，Pipeline 也能加
………………

然后这些 Feature 被塞进一个 IFeatureCollection（本质就是个 Dictionary<Type, object>）。Pipeline 通过这个字典拿它需要的接口：

// Kestrel Pipeline 里的典型用法
var requestFeature = context.Features.Get<IHttpRequestFeature>();
var responseFeature = context.Features.Get<IHttpResponseFeature>();

if (requestFeature.Path == "/hello") {
    responseFeature.StatusCode = 200;
    await responseFeature.Body.WriteAsync(Encoding.UTF8.GetBytes("Hello!"));
}

为什么用接口字典？而不是一个大 HttpContext？

你可能会问：为什么不直接传一个 HttpContext 类，里面啥都有？三个原因：

① 协议层透明

Pipeline 里写的 context.Features.Get<IHttpRequestFeature>()，底层可能是 Http1Connection 填的，也可能是 Http2Connection 填的，也可能是 Http3Connection 填的 —— Pipeline 不在乎。接口隔离了协议差异。

② 可选功能按需加载

如果一个 Feature 不存在（比如 HTTP/1.1 连接没有 TLS，就不会有 ITlsConnectionFeature），Get<T>() 返回 null。Pipeline 可以优雅降级，而 HttpContext 大对象不管用不用都得 new 出来。

③ 第三方扩展零侵入

任何中间件都可以加自定义 Feature —— 比如你想加一个 ISqlConnectionFeature 让下游中间件共享一个数据库连接池的连接，只需要在 Pipeline 前面的中间件里 context.Features.Set<ISqlConnectionFeature>(conn)，下游就能 Get 到。HttpContext 大对象做不到这一点。

Pipeline 是什么？

Pipeline 就是一组 Application 中间件。在我们的简化版里，就是这么一个接口：

// 简化版 Pipeline 接口
// Kestrel 里对应的是 IHttpApplication + RequestDelegate 链

public interface IHttpApplication
{
    Task ProcessRequestAsync(IFeatureCollection features);
}

Connection 不路由、不生成响应，它只做：

// Connection.StartAsync 现在的伪代码
public async Task StartAsync(CancellationToken ct) {
    while (true) {
        var request = await ReadAndParseAsync(ct);

        // ① 填 Features（Protocol Layer 的事）
        var features = new FeatureCollection();
        features.Set<IHttpRequestFeature>(new HttpRequestFeature(request));
        features.Set<IHttpResponseFeature>(new HttpResponseFeature());
        features.Set<IHttpConnectionFeature>(new HttpConnectionFeature(_transport));

        // ② 交给 Pipeline（Application Layer 的事）
        await _application.ProcessRequestAsync(features);

        // ③ 从 Features 里取 Pipeline 填好的响应，序列化写回
        var response = features.Get<IHttpResponseFeature>();
        await WriteResponseAsync(response, ct);

        // ④ 判断 Keep-Alive ...
    }
}

现在四层架构全貌

① KestrelServer — Accept 循环（Program.cs）
↓ new SocketTransport(socket)
② Transport — SocketTransport 提供 Read/Write 字节通道
↓ 构造函数注入 ITransportConnection
③ Protocol — HttpConnection 读/解析/填 Features
↓ IFeatureCollection（接口字典，这就是层间契约！）
④ Application — Pipeline 路由 + 生成响应

注意 IFeatureCollection 是第 ③ 和第 ④ 层之间的 唯一 交互方式。Protocol 层不知道 Pipeline 是什么，Pipeline 层不知道 Connection 是什么 —— 两边只通过 Feature 接口字典"说话"。

Kestrel 源码里的对应

  • 👉 src/Features/IHttpRequestFeature.cs — Kestrel 的请求特性接口。只有 get/set 属性，没有方法
  • 👉 src/Features/IFeatureCollection.cs — 接口字典，核心是 T Get<T>() / void Set<T>(T feature)
  • 👉 src/Features/FeatureReferences<TContext>.cs — Kestrel 2.0+ 的 Feature 引用缓存。每次 Get 要查字典太慢，Kestrel 在 Connection 对象上缓存常用 Feature 的引用，避免重复查表。这是个重要的性能优化点
  • 👉 Http1Connection.ProcessRequestAsync() — 看它怎么把 HttpRequest 和 HttpResponse 填进 Feature，然后调 _httpApplication.ProcessRequestAsync(context)。这就是我们要做的事

🎯 动手改造清单

  1. 新建 Features 目录和接口文件：IHttpRequestFeature、IHttpResponseFeature、IHttpConnectionFeature
  2. 新建 FeatureCollection.cs — Dictionary<Type, object> 包装
  3. 新建 IHttpApplication.cs + SimpleMiddleware.cs — Pipeline 接口和实现
  4. 重构 HttpConnection.cs：构造函数多接收一个 IHttpApplication，删除 HandleRequest 方法，改成填 Features → 调 Application → 写响应
  5. 改 Program.cs：配置路由成 SimpleMiddleware，传给 HttpConnection

重构自检

  • ✅ HttpConnection.cs 里不再出现路由逻辑（switch on Path → response text）
  • ✅ HttpConnection.cs 里不再创建 HttpResponse 并 SetText
  • ✅ SimpleMiddleware.cs 里能看到所有路由逻辑
  • ✅ HttpConnection 和 SimpleMiddleware 互相不知道对方的具体类型

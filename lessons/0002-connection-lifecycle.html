第 02 课 · ConnectionContext 生命周期

预计阅读 12 分钟 动手重构 从函数 → 对象

上节课的代码有什么问题？

我们的基线服务器，HandleConnectionAsync 是个 static 方法：

static async Task HandleConnectionAsync(Socket client) {
    using (client) {
        // 读请求、解析、写响应 —— 全塞在这一个方法里
    }
}

能跑，但有个根本问题：连接的状态无处安放。

想一想，如果要加这些功能，你怎么办：

  • ✅ Keep-Alive：一个 TCP 连接上连续处理多个 HTTP 请求。你得在循环里不断读请求，直到客户端说 Connection: close 或超时。"当前读到第几个请求了"这个状态放哪？
  • ✅ 连接超时检测：连接空闲 60 秒就关掉。谁来跟踪"上次活动时间"？
  • ✅ WebSocket 升级：HTTP 请求升级到 WebSocket 后，同一个 Socket 上不再是 HTTP 协议，而是二进制帧。状态机怎么切换？
  • ✅ 连接统计：想知道某个连接处理了多少请求、总字节数多少。放 static 变量？那所有连接共享，没法做单连接统计。
Kestrel 的解法：把"一个 TCP 连接"变成一个对象，就是 ConnectionContext。每个 Socket 对应一个实例，所有与这个连接相关的状态、配置、协议处理器，全挂在这个对象上。

ConnectionContext 到底是什么？

源码位置：dotnet/aspnetcore / src / Servers / Kestrel / Core / ConnectionContext.cs

简化后它大概长这样（我加了注释解释每个成员干嘛的）：

public abstract class ConnectionContext : IAsyncDisposable
{
    // ===== 传输层 =====
    public TransportConnection Transport { get; set; }
    // 这个连接的 Socket 抽象（或 QUIC、或 pipe）

    // ===== 协议层 =====
    public IProtocolProtocol Protocol { get; set; }
    // 可以是 Http1Connection / Http2Connection / Http3Connection
    // 甚至可以是 WebSocketProtocol、SignalRProtocol...

    // ===== Feature 集合（给 Pipeline 用的）=====
    public IFeatureCollection Features { get; }
    // IHttpRequestFeature, IHttpResponseFeature,
    // IHttpConnectionFeature, ITlsConnectionFeature ...
    // Pipeline 通过 Features 获取请求/响应，不碰底层 Socket

    // ===== 连接状态 =====
    public DateTimeOffset LastActivityTimestamp { get; set; }
    // 上次读写活动时间，超时检测用

    public CancellationToken ConnectionClosed { get; protected set; }
    // 连接关闭时触发，让 Pipeline 里的服务及时清理

    // ===== 关键方法 =====
    public abstract Task StartAsync(CancellationToken cancellationToken);
    // 启动连接主循环（读请求 → 处理 → 写响应）

    public abstract Task StopAsync(CancellationToken cancellationToken);
    // 关闭连接，释放资源

    public abstract ValueTask DisposeAsync();
    // 实现 IAsyncDisposable，资源清理
}

核心设计思路是三句话：

1. 一个连接 = 一个实例：ConnectionContext 的生命周期 = TCP 连接的生命周期。Socket.Accept → new ConnectionContext → StartAsync → StopAsync → Dispose。一对一。

2. 三层分离：Transport 管底层 Socket；Protocol 管字节到 HTTP 语义的转换；Features 管向上暴露的抽象。三层通过 ConnectionContext 协调，互不反向依赖。

3. Features 字典 = 万能包：Pipeline 只认 Features，不认底下是 HTTP/1.1 还是 HTTP/2，不认底下是 Socket 还是 QUIC。这是 Kestrel 可扩展的关键。

Connection 生命周期状态机

一个 ConnectionContext 从创建到销毁，大致经历这些阶段：

[New] Socket.Accept 成功，new ConnectionContext()
↓
[Starting] StartAsync() — 配置协议、注册 Features、启动主循环
↓
[Running] 主循环：Read → Parse → Dispatch → WriteResponse（可处理 N 个请求）
↓ 任意终止条件触发
[Stopping] StopAsync() — 通知 Pipeline、关闭 Socket
↓
[Disposed] DisposeAsync() — 释放所有资源

"任意终止条件"包括：

  • 客户端主动关闭（ReceiveAsync 返回 0）
  • Keep-Alive 超时（LastActivityTimestamp 检查）
  • Pipeline 内部触发 Connection.RequestAborted
  • 服务器收到停机信号

🎯 动手：把你的服务器改成 Connection 对象

现在轮到你重构。把上节课的 HandleConnectionAsync 拆成一个类 HttpConnection，满足这个接口：

// 我们的简化版 ConnectionContext
public class HttpConnection : IAsyncDisposable
{
    private readonly Socket _socket;

    // 构造函数：接收新 Socket
    public HttpConnection(Socket socket);

    // 主入口：启动连接处理循环
    public async Task StartAsync(CancellationToken ct = default);

    // 实现 IAsyncDisposable
    public async ValueTask DisposeAsync();

    // ===== 内部成员 =====
    // - LastActivity 时间戳（为 Keep-Alive 做准备）
    // - 当前连接处理的请求计数
    // - 一个私有方法 ParseRequest(byte[]) → Request 对象
    // - 一个私有方法 HandleRequest(Request) → Response 对象
    // - 一个私有方法 WriteResponse(Response)
}

同时，Program.cs 的 Accept 循环应该变成：

while (true) {
    var client = await listener.AcceptAsync();
    var conn = new HttpConnection(client);
    _ = conn.StartAsync();
    // 注意：这里我们不再手动 Dispose，让 HttpConnection 自己管理生命周期
    // 它在 StartAsync 内部结束时会调 DisposeAsync
}
重构目标：
1. HttpConnection 类独立成文件（推荐新建 HttpConnection.cs）
2. 有一个简单的 HttpRequest POCO 类（Method, Path, Headers 字典）
3. 有一个简单的 HttpResponse POCO 类（StatusCode, Body 字节数组）
4. Program.cs 只留 Accept 循环和配置路由的代码

重构后的项目结构

MinimalHttpServer/
├── Program.cs          ← 只有 Accept 循环 + 路由配置
├── HttpConnection.cs   ← Connection 生命周期管理
├── HttpRequest.cs      ← 请求对象（POCO）
├── HttpResponse.cs     ← 响应对象（POCO）
├── HttpParser.cs       ← 从 Socket 字节解析出 HttpRequest
└── MinimalHttpServer.csproj

注意这个拆法：Program.cs 对应 Kestrel 的 KestrelServer；HttpConnection 对应 Kestrel 的 ConnectionContext；HttpParser 对应 Kestrel 的 Protocol Layer。这就是我们"逼近 Kestrel 架构"的路线。

一个提醒：Features 字典我们还没做

你可能注意到了，Kestrel 的 ConnectionContext 有个 Features 字典，但我们现在没有。这是故意的——

Features 字典是 Kestrel 的核心抽象，但引入它之前你需要先理解一件事："请求/响应对象"和"Feature 接口集合"到底是什么关系。我们在这节课先把 Connection 生命周期理顺，下节课（Keep-Alive 那课）会引入 Features。过早引入会让你混淆"为了什么而设计"。

Kestrel 源码阅读锚点

读完这一课，你应该能在 Kestrel 源码里找到这些东西：

  • 👉 ConnectionContext.cs — 我们的基类设计就来自这里。重点看它抽象属性的定义，感受它如何不依赖任何具体 Transport。
  • 👉 DefaultConnectionContext.cs — ConnectionContext 的默认实现。看它的 StartAsync 怎么把 Transport 和 Protocol 接起来。
  • 👉 KestrelServerImpl.cs 里的 AcceptLoopAsync — 看 Accept 之后怎么 new ConnectionContext 并 StartAsync。这是 KestrelServer → ConnectionFactory 的桥梁。
推荐阅读顺序：KestrelServerImpl.AcceptLoopAsync → 跟进去看 ConnectionFactory.CreateConnection → 跟进去看 ConnectionContext.StartAsync → 看到它选了 Http1Connection 还是 Http2Connection。一条链读到底，你就通了。

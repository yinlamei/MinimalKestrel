第 06 课 · 性能对比 —— 我们的 vs Kestrel

预计阅读 15 分钟 实测 + 分析 所有课程的最终验证

为什么要测性能？

到 v0.5 为止，我们的 MinimalHttpServer 架构上已经和 Kestrel 四层对齐了：

  • ✅ Transport 抽象层 — 有
  • ✅ Connection 对象化 + Keep-Alive — 有
  • ✅ HttpParser 状态解析 — 有（虽然简陋）
  • ✅ Feature 字典 + Pipeline — 有

但架构对齐 ≠ 性能对齐。Kestrel 每秒能处理几十万请求，我们这个估计几千就到头了。差距在哪？这节课通过实测来回答。

测试方法

我们测三个服务器，同一个简单 GET 请求 /hello（返回固定文本），保持 Keep-Alive，测 QPS：

服务器说明
MinimalHttpServer我们的 v0.5 实现 — Socket + 朴素 ReadAsync + 朴素 Parser
HttpListener.NET 内置的 HTTP 监听器（System.Net.HttpListener）— 传统做法
KestrelASP.NET Core 默认 Web 服务器 — 业界最佳实践

用 BenchmarkDotNet 写一个统一的客户端压测，三个服务器分别跑。测两个维度：

  1. 单次请求延迟（ns）— 最小开销
  2. 并发 QPS — 吞吐量

先猜一猜：差距可能在哪？

在跑 Benchmark 之前，我们先做一轮"性能头脑风暴" — 想想 Kestrel 可能在哪些地方比我们快：

① 内存分配

我们的 ReadFullRequestAsync 每次都 new byte[8192]，HttpParser.Parse 每次都 Split("\r\n")，FeatureCollection 每次 new。一次请求下来可能分配几十 KB 临时对象。

Kestrel 怎么做的？

  • 用 MemoryPool<byte> 从池中租借内存，用完归还，零分配
  • 用 Pipe 替代 Stream，PipeReader/PipeWriter 共享内存段，零拷贝
  • HttpParser 状态机逐字节解析，直接在 Pipe 的内存段上原地操作，不 Split 不 new
  • FeatureReferences<TContext> 缓存 Feature 接口引用，避免每次 Get 查字典

② Socket 开销

我们每次 Read 都是 await _socket.ReceiveAsync(buffer, ct) — 每个请求 await 至少 2-3 次（读头部 + 可能读 Body）。每次 await 都会让 IOCP 线程池调度一次。

Kestrel 怎么做的？

  • SocketAwaitable — 自定义 awaitable，不分配 Task 对象，避免每次 await 的堆分配
  • Transport 层后台跑 持续搬运循环：一个循环从 Socket 读 → PipeWriter.Write → PipeWriter.FlushAsync；另一个循环 PipeReader.ReadAsync → Socket.SendAsync。Connection 层只和 Pipe 交互，不碰 Socket
  • PipeReader.ReadAsync(Min, Max) — 支持"至少给我 Min 字节"的语义，避免每次只 Read 一点就触发解析

③ 解析器开销

我们用 Encoding.UTF8.GetString → Split("\r\n") → Split(':') — 多次字符串分配 + 多次遍历。Kestrel 用 HttpParser 状态机直接在 byte span 上解析，零字符串分配直到真正需要 ToString 时。

④ 背压与流控制

我们没做背压 — Pipeline 写响应比 Socket 发得快时，数据会堆在内核缓冲区。Pipe 有内置背压：PipeWriter.Write 超过阈值时会阻塞，自然让 Pipeline 等 Socket 追上来。

⑤ 连接池与复用

我们每次 Accept → new SocketTransport → new HttpConnection → new FeatureCollection → new HttpRequest → new HttpResponse → new HttpRequestFeature → new HttpResponseFeature。十几个对象。

Kestrel 对很多对象做了 池化：ConnectionContext、Http1Connection 甚至 FeatureCollection。连接断开后对象不是直接 GC，而是归还对象池，下次 Accept 取出来复用。

🎯 动手：跑 Benchmark

我已经准备好了一个 Benchmark 项目，包含三个服务器实现和一个压测客户端。先跑起来看数据，再对照上面的猜测。

运行 Benchmark：
dotnet run --project ./benchmark/HttpPerfBenchmark -c Release
观察输出的 QPS、单次请求耗时、以及 Allocations 列 —— 差距会很明显。

Kestrel 源码里的性能关键点

对照 Benchmark 结果，去 Kestrel 源码里找对应的优化：

  • 👉 SocketSender.ReceiveAsync / SocketSender.SendAsync — 自定义 SocketAwaitable，零 Task 分配
  • 👉 HttpParser.ParseRequestLine — 状态机逐字节解析 Span<byte>，零分配
  • 👉 FeatureReferences<TContext> — 在 Connection 对象上缓存常用 Feature 引用，结构体重叠排列
  • 👉 MemoryPool<byte>. — Kestrel 默认用 SlabMemoryPool，按 slab 块出租，减少 GC 压力
  • 👉 Transport 层的 PipeReader/CopyToAsync 和 PipeWriter.CopyToAsync — 后台搬运循环

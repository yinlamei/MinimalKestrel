第 01 课 · Kestrel 架构心智模型

预计阅读 15 分钟 源码阅读入门 先建立地图，再读代码

先写个"你以为的"服务器

有 15 年 C# 经验，让你写一个最简 HTTP 服务器，大概 30 行代码就能搞定：

using var listener = new Socket(AddressFamily.InterNetwork,
    SocketType.Stream, ProtocolType.Tcp);
listener.Bind(new IPEndPoint(IPAddress.Loopback, 8080));
listener.Listen(100);

while (true) {
    var client = await listener.AcceptAsync();
    _ = HandleRequestAsync(client);  // fire-and-forget
}

async Task HandleRequestAsync(Socket client) {
    using (client) {
        var buf = new byte[4096];
        var n = await client.ReceiveAsync(buf);
        var request = Encoding.UTF8.GetString(buf, 0, n);
        // 简单解析：第一行 Method + Path
        var path = request.Split(' ')[1];
        var body = $"Hello {path}".ToBytes();
        var resp = $"HTTP/1.1 200 OK\r\nContent-Length: {body.Length}\r\n\r\n".ToBytes();
        await client.SendAsync(resp);
        await client.SendAsync(body);
    }
}

这能跑。curl 一下有响应。但——这不是 Kestrel 的风格，差距在于：

Kestrel 的核心设计哲学是"为每个变化维度建一层抽象"。上面 30 行代码把监听、连接、解析、应用逻辑全耦合在一起了；Kestrel 把它们拆成了四层，每层独立演化。

Kestrel 四层架构

① KestrelServer （入口：启动监听循环）
↓ Accept / AcceptAsync
② Transport + ConnectionFactory （传输层 + 连接管理）
↓ 创建 ConnectionContext
③ Protocol Layer （协议解析：Http1 / Http2 / Quic）
↓ 将 Socket 字节流解析为 IHttpRequest / IHttpResponse 特性
④ Application Pipeline （中间件管道：Minimal API / MVC / WebSocket）

这四层之间只有向上依赖，不反向耦合。下面逐层拆给你看。

① KestrelServer — 监听入口

源码位置：src/Servers/Kestrel/Core/KestrelServer.cs

这是整个服务器的起点。核心就是循环调用 Transport.BindAsync() 然后不断 Accept，把新连接交给 ConnectionFactory。它只做两件事：

  • 根据 KestrelServerOptions 配置端口、绑定地址、证书
  • 启动 Accept 循环，把 Socket 交给 ConnectionFactory
关键洞察：KestrelServer 本身不持有任何连接。它只管 Accept，Accept 之后的事全丢给 ConnectionFactory。这让它能同时监听多个端口（HTTPS + HTTP 同进程），也能在不停服的情况下重新加载配置。

② Transport + ConnectionFactory — 传输抽象 + 连接管理

这是 Kestrel 最聪明的一层。

Transport 是底层传输方式的抽象。Kestrel 支持多种传输：

  • SocketsTransport — 现在默认的，纯托管 Socket
  • QuicTransport — HTTP/3 的 QUIC 传输
  • 历史上有 LibuvTransport（已弃用，Kestrel 1.x 时代用的 libuv）

ConnectionFactory 的职责是：每收到一个新 Socket，创建一个 ConnectionContext。ConnectionContext 是一次 TCP 连接的全部状态容器——它持有 Transport、协议处理器、以及在 Application Pipeline 中流转的所有 Feature。

// ConnectionFactory 的核心逻辑（简化）
public ConnectionContext CreateConnection(TransportConnection transport) {
    var context = new DefaultConnectionContext(transport);
    // 配置协议层：Http1Connection 或 Http2Connection
    context.ConfigureProtocol(this);
    return context;
}
// 然后调用 ConnectionContext.StartAsync() 启动连接处理循环
关键洞察：ConnectionContext 是整个设计的"胶水"。它是 Transport 层和 Protocol 层之间的桥梁，也是异步管道的起点。每个 TCP 连接对应一个 ConnectionContext，生命周期严格对齐。

③ Protocol Layer — HTTP 协议解析

源码位置：src/Servers/Kestrel/Http/ 目录

Kestrel 支持三种协议，每种都有独立的实现：

协议实现类解析方式
HTTP/1.1Http1Connection逐字节解析，状态机驱动
HTTP/2Http2Connection帧解析 + HPACK 头部压缩
HTTP/3 (Quic)Http3ConnectionQUIC 流 + HTTP/3 帧

这一层的输入是 Socket 字节流，输出是一组标准化的 Feature：IHttpRequestFeature、IHttpResponseFeature、IHttpConnectionFeature 等。上层中间件不关心底下跑的是 HTTP/1.1 还是 HTTP/2。

④ Application Pipeline — 中间件管道

这一层你应该最熟悉。ConnectionContext 的协议层把 Feature 填好之后，调用 IHttpApplication.ProcessRequestAsync(features)。

这里的 IHttpApplication 就是你在 Program.cs 里 app.UseRouting().UseEndpoints() 堆出来的中间件管道。Kestrel 不知道 MVC、不知道 Minimal API，它只认这个接口。

朴素 Socket vs Kestrel：到底差在哪？

维度朴素 Socket 循环Kestrel 设计
监听 & Acceptwhile + async void fire-and-forgetAccept 循环 + ConnectionFactory 统一管理
协议解析Split(' ') 搞定状态机驱动的 Http1Parser，逐字节零分配解析
传输切换换 QUIC = 全重写Transport 抽象，一行配置切换
连接管理无（依赖 GC 收 Socket）ConnectionContext + 后台 Ping 检测
内存分配new byte[4096] per requestSocketAwaitable + 内存池复用
WebSocket自己搞握手和帧协议层直接支持 Feature
HTTP/2不支持同一套 Pipeline，协议层透明

dotnet/aspnetcore/src/Servers/Kestrel/

│   ├── KestrelServerOptions.cs    ← 配置模型

├── Http/
│   ├── Http1Connection.cs         ← HTTP/1.1 协议处理核心
│   ├── Http2Connection.cs         ← HTTP/2

阅读建议：先读 KestrelServerImpl.AcceptLoopAsync()，跟着一个新 Socket 一路追踪：谁创建 ConnectionContext、谁选协议、谁触发 Pipeline。这个调用链通了，你对 Kestrel 就有骨架了。

🎯 动手练习

现在轮到你。写一个最简 Socket HTTP 服务器，满足以下要求：

  • 监听 http://localhost:8080
  • 支持并发：每个新连接启动一个独立处理任务（不要阻塞 Accept）
  • 解析 GET 请求，支持 3 个路由：/、/hello、/time
  • 返回正确的 Content-Length 头部和 \r\n\r\n 分隔符
  • 处理好连接关闭（using Socket，或者 Timeout 自动关闭）

写完之后对照你的实现和 Kestrel 的四层架构，思考：

  1. 你的代码里，"Transport" 是哪个类？如果要把 Socket 换成 QUIC，要改哪些地方？
  2. 你的"Protocol Layer"在哪里？能拆出来吗？
  3. 如果要支持 HTTP/2，你的架构要做什么调整？
创建一个 console 项目：dotnet new console -n MinimalHttpServer，把上面的代码骨架跑起来。

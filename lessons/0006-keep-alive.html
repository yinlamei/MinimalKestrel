第 03 课 · Keep-Alive — 一个连接处理 N 个请求

预计阅读 12 分钟 动手改造 Connection 对象化第一次真正"有用"

HTTP/1.0 时代：每次请求都是新 TCP 连接

在最早的 HTTP/1.0 里，一个请求 = 一个 TCP 连接。浏览器加载一个页面，可能要发起 50 次请求（HTML + CSS + JS + 图片），意味着 50 次 TCP 三次握手 + 50 次 TLS 握手 + 50 次四次挥手。

TCP 三次握手 ≈ 1-2 RTT（往返延迟），TLS 握手再加 2 RTT。对于跨洋请求，光建立连接就要几百毫秒，而 HTTP 请求本身可能只用几十毫秒。绝大多数时间浪费在连接上了。

HTTP/1.1 的解决方案就是 Persistent Connection（持久连接），俗称 Keep-Alive：一个 TCP 连接上顺序发送/接收多个 HTTP 请求/响应，直到客户端或服务器显式关闭。

所以这节课的目标很简单：把我们的 HttpConnection.StartAsync 从"单次 Read → Handle → Write"改成一个循环：

// 之前（v0.2）
public async Task StartAsync(CancellationToken ct) {
    var req = await ReadRequestAsync(ct);
    if (req == null) return;
    var resp = HandleRequest(req);
    await WriteResponseAsync(resp, ct);
    // 一次就结束，然后 Dispose
}

// 之后（v0.3 Keep-Alive）
public async Task StartAsync(CancellationToken ct) {
    while (true) {
        // 1. 检查空闲超时 → 超时就 break
        // 2. 读一个完整请求 → 客户端断连就 break
        var req = await ReadRequestAsync(ct);
        if (req == null) break;

        // 3. 处理并写回
        var resp = HandleRequest(req);
        await WriteResponseAsync(resp, ct);

        // 4. 检查 Connection 头部 → close 就 break，keep-alive 就继续循环
        if (req.Headers.TryGetValue("Connection", out var conn)
            && conn.Equals("close", StringComparison.OrdinalIgnoreCase))
            break;

        // 5. 默认 HTTP/1.1 = keep-alive，继续 while 循环
    }
    // while 退出后 Dispose 自然被 RunConnectionAsync 里的 finally 调用
}

三个必须解决的问题

① 怎么知道"一个请求"什么时候读完？

上节课的 ReadRequestAsync 只读到 \r\n\r\n（头部结束）就停了。但 HTTP 请求不止有头部，还有可能有 Body（POST/PUT 会带）。所以完整的"读一个请求"分两步：

  1. 读头部：找到 \r\n\r\n 为止 —— 和以前一样
  2. 读 Body：根据头部决定怎么读

Body 有两种传输方式，由头部指定：

头部含义怎么读
Content-Length: 42Body 固定 42 字节头部之后再读 exactly 42 字节
Transfer-Encoding: chunked分块传输需要解析 chunk 格式（下节课再说）
都没有无 Body头部读完就够了
关键洞察：Keep-Alive 循环能持续运行的前提是，你必须能精确地知道"上一个请求结束了没有"，才能正确定位"下一个请求从哪个字节开始"。如果 Content-Length 读错了，Socket 流里的字节对齐就崩了，整个连接废了。这也是 Kestrel HttpParser 用状态机逐字节解析的原因 —— 它不依赖一次性 Read 的边界。

② 怎么让循环停下来？

有五种退出条件，按概率排序：

  • 🔵 客户端关闭连接：ReceiveAsync 返回 0 字节 — 最常见
  • 🟢 客户端发送 Connection: close — 正常关闭约定
  • 🟡 空闲超时：LastActivity 超过阈值（例如 60 秒）— 服务器主动关
  • 🔴 收到非法请求：解析失败，服务器返回 400 然后关连接
  • ⚫ 服务器停机：CancellationToken 被触发

③ 超时时谁来检查？

这是个容易忽略的细节。我们的 while 循环里有一个 await ReadRequestAsync，它会阻塞在 ReceiveAsync 上等待下一个请求。如果客户端不发也不关，我们就一直卡在这里 —— 那"每 60 秒检查一次超时"怎么实现？

两种做法：

  • A. 给 Socket 设 ReceiveTimeout：超过 X 秒没数据，Socket.ReceiveAsync 抛异常。简单，但异常驱动超时不是 Kestrel 的风格。
  • B. 给 CancellationToken 加超时：每次 ReadRequestAsync 前创建一个 new CancellationTokenSource(idleTimeout)，Read 时传这个 Token。超时 → OperationCanceledException → while 循环 catch 后 break。

Kestrel 用的是 B 方案 — 因为它同时还要响应"服务器全局停机"和"连接级超时"两种取消信号，CancellationToken 是 .NET 里做这个的正统方式。

超时检测的实现

// 在 HttpConnection 里加一个字段
private readonly TimeSpan _idleTimeout = TimeSpan.FromSeconds(30); // 练习用短点

// 然后 StartAsync 里每次 Read 都包一层超时 token
public async Task StartAsync(CancellationToken globalCt) {
    while (true) {
        // 每次读请求都有独立的空闲超时
        using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(globalCt);
        timeoutCts.CancelAfter(_idleTimeout);

        HttpRequest request;
        try {
            request = await ReadRequestAsync(timeoutCts.Token);
        }
        catch (OperationCanceledException) {
            if (timeoutCts.IsCancellationRequested) {
                Console.WriteLine("连接空闲超时，关闭");
            }
            break;
        }

        if (request == null) break; // 客户端断连
        // ... Handle + Write ...
        // ... Connection: close 判断 ...
    }
}

Kestrel 源码里的对应实现

Keep-Alive 循环在 Kestrel 里的核心是 Http1Connection.ProcessRequestsAsync()，它就是一个巨大的 while 循环。去找这些东西：

  • 👉 Http1Connection.cs 里的 ProcessRequestsAsync() 方法 —— 就是我们 while(true) 的原型
  • 👉 里面的 KeepAliveAsync 方法 —— 专门处理 keep-alive 超时等待，和我们的超时 CTS 同理
  • 👉 HttpParser.cs 里的 ParseHeaders 方法 —— Kestrel 怎么从 Socket 流里精确读取头部，它用的是 ParsingState 枚举驱动的状态机
  • 👉 Http1Connection.Input.ReadAsync(Min, Max) —— Kestrel 不是一次性读完头部，而是"请至少给我 Min 字节，最多给我 Max 字节"，配合 SocketAwaitable 做零分配缓冲
Kestrel 的 Body 读取更复杂。它支持：Content-Length、Transfer-Encoding: chunked、HTTP/2 帧化 Body、Upgrade 后的原始 Stream、以及各种组合。而我们这节课先只做 Content-Length，chunked 留到下一课。

🎯 动手改造清单

  1. 在 HttpConnection 里加 _idleTimeout 字段和构造函数参数
  2. 把 StartAsync 改成 while(true) 循环，每次循环创建新的超时 CTS
  3. 异常处理：OperationCanceledException 区分是 timeout 还是 globalCt
  4. ReadRequestAsync 需要读取完整 Body（Content-Length），返回的 HttpRequest.Body 要填好
  5. WriteResponse 时自动设置 Connection: keep-alive（如果不是最后一个请求）
  6. 加上请求计数日志，方便你验证一个连接上跑了多个请求

改完之后，你可以用这个 curl 命令验证 Keep-Alive：

curl http://localhost:8080/hello && curl http://localhost:8080/time && curl http://localhost:8080/

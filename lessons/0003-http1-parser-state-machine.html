第 03 课 · Http1Parser —— 从 Split 到状态机

预计阅读 20 分钟 Kestrel 性能核心秘密 零分配解析

我们现在的 HttpParser 做了什么？

打开你的 HttpParser.cs，Parse() 方法：

// 当前写法（朴素版）
var headerText = Encoding.UTF8.GetString(buffer, 0, headerEnd);  // ① 把全部头部转成字符串
var lines = headerText.Split("\r\n", StringSplitOptions.None);     // ② 按 \r\n 拆行
var firstLine = lines[0];
var parts = firstLine.Split(' ');                                  // ③ 按空格拆请求行
...
for (int i = 1; i < lines.Length; i++) {
    var colonIdx = line.IndexOf(':');                              // ④ 找冒号
    var key = line[..colonIdx].Trim();                             // ⑤ Substring 分配新字符串
    var value = line[(colonIdx + 1)..].Trim();                     // ⑥ 又 Substring
}

一个请求进来，我们至少做了这些分配：

  1. 整个头部 → 一个 字符串（可能几百字节）
  2. Split("\r\n") → N 个 字符串数组元素
  3. 请求行 Split(' ') → 3 个 字符串
  4. 每个 Header → 2 个 字符串（Key + Value）
  5. Trim() → 可能又 新字符串

一个简单 GET 请求，头部 300 字节，至少分配 10+ 个堆对象。这就是 GC 压力的来源。

Kestrel 怎么做？状态机逐字节解析

Kestrel 的 HttpParser 源码：dotnet/aspnetcore / src / Servers / Kestrel / Http / Shared / HttpParser.cs（约 2000 行）。核心是一个枚举驱动的状态机：

// Kestrel HttpParser 的状态枚举（简化）
enum ParsingState
{
    RequestLineStart,          // 等待请求行开始
    RequestLineAfterSpace,     // 读完 Method，等 /
    RequestLineHttp,           // 读完 Path，等 HTTP/
    RequestLineVersion,        // 正在读 HTTP/1.1
    HeaderName,                // 正在读 Header-Name
    HeaderValueStart,          // 读完冒号+空格，等 Value 开始
    HeaderValue,               // 正在读 Value
    HeaderValueEndingCR,       // 等 \r（可能 \r\n\r\n 头部结束）
    HeaderValueEndingLF,       // 等 \n
    HeadersComplete,           // 头部全读完了
    Body                       // 开始读 Body（Content-Length）
}

状态机逐字节读 byte buffer，**全程不转字符串**。每个字节直接比较数字值：

// byte 值速查 — ASCII
byte CR = 13;   // '\r'
byte LF = 10;   // '\n'
byte COLON = 58; // ':'
byte SPACE = 32; // ' '
byte SLASH = 47; // '/'

请求行解析的状态机动画

  GET /hello HTTP/1.1\r\n
  ↑   ↑            ↑  ↑
  |   |            |  └── 字节 15 = LF → 状态 HeaderName
  |   |            └────── 字节 12 = SP, 13/14 = '1','.' → 状态 RequestLineVersion
  |   └─── 字节 4 = SLASH → 开始读 Path，直到遇到 SP
  └─────── 字节 0-2 = 'G','E','T' → 枚举查表 Method

状态机为什么快？三个原因

① 零字符串分配

Kestrel 在解析阶段**根本不 new string**。Method 用枚举（HttpMethod.Get = 0），Header Name 用预定义常量（KnownHeaders.ContentLength），只存 start index + length 表示一个头部在 buffer 里的位置。只有到真正需要字符串时（比如 Pipeline 里 context.Request.Path）才延迟转换。

② 流式处理

朴素版 FindHeaderEnd 假定头部完整到达。但 TCP 不保证 —— 第一次 Receive 可能只到 GET /hello HT，第二次才到 TP/1.1\r\nHost: localhost\r\n\r\n。状态机天然支持这种**流式增量解析**：上次停在 RequestLineHttp 状态，下次从同一状态继续。

③ 没有无效遍历

朴素版每读一个新 buffer 都从头 for i in buffer 找 \r\n\r\n，重复扫描已读的部分。状态机只往前走，看过的字节不再看。

🎯 动手：写一个简化版状态机 HttpParser

我们自己实现一个！不追求 Kestrel 的完整度（它支持 chunked、pipelining、HTTP/2 升级、trailers...），但核心思想一样。支持：

  • ✅ 逐字节状态机解析请求行（Method, Path, Version）
  • ✅ 逐字节解析 Header（Key + Value）
  • ✅ 流式增量 — 可以先给一半数据，再给另一半
  • ✅ 不分配头部字符串（用 span 切片）
  • ❌ Body 解析暂时忽略（先做头部）
  • ❌ chunked transfer encoding 暂时不做

核心 API 设计：

// 状态机 parser 是有状态的 — 每传一批字节进来，它前进一段
public class Http1Parser
{
    private ParsingState _state = ParsingState.RequestLineStart;
    private int _bufferPos;           // 当前读到 buffer 的哪个位置
    private byte[]? _buffer;          // 当前正在解析的 buffer
    private int _requestStart;        // 这次请求在 buffer 里的起始位置

    // 累计的请求数据
    public string Method { get; private set; } = "";
    public string Path { get; private set; } = "";
    public string Version { get; private set; } = "";
    public Dictionary<string, string> Headers { get; } = new();
    public int HeaderEnd { get; private set; } = -1; // 头部在 buffer 里的结束位置（Body 起点）

    /// <summary>
    /// 喂一批新字节进去。返回 true 表示头部解析完成。
    /// 可以多次调用 Parse，每次给新数据（流式增量）。
    /// </summary>
    public bool Parse(ReadOnlySpan<byte> data);

    /// <summary>
    /// 解析完成后，调用 Reset 开始下一轮（Keep-Alive 场景）
    /// </summary>
    public void Reset();
}

Kestrel 源码锚点

  • 👉 src/Servers/Kestrel/Http/Shared/HttpParser.cs — 约 2000 行，完整状态机。先看 ParsingState 枚举和 ParseRequestLine 方法，这是我们这一课实现的核心参考
  • 👉 对比我们的简化版和 Kestrel 版，你会发现它多了：对 \r\n 可能出现在请求行中间的防御逻辑、Header fold 处理（旧版 HTTP 特性）、对 Transfer-Encoding: chunked 的状态机、HTTP/2 升级、 trailers 支持
Kestrel HttpParser 一个有趣的细节：它对 Header Value 有一个 HeaderValueEndingCR 状态 — 这是为了处理"假 \r\n"场景：如果一个 Header Value 里有 CR，状态机要多走两步才能确定这是真的行结束还是数据里的字节。HTTP 解析的坑比看起来多得多。
